# 权限延时开通：时间轮还是 XXL-JOB

## 结论

**这个场景用 XXL-JOB 更合适**，用法是：**一条（或少量）定时任务，按到期时间扫库、批量开通**。不要为每个购买用户建一条 XXL-JOB，也不要把时间轮当成权威调度器。

`lind-delay-task-web` 的时间轮适合「单机内存里大量短延时回调」；权限开通是履约，丢一次或重复开一次都有业务后果，权威数据应在订单/权益表，触发用定时扫表更稳。

## 两种东西实际在干什么


|       | [lind-delay-task-web](lind-delay-task-web) 时间轮                        | XXL-JOB                        |
| ----- | --------------------------------------------------------------------- | ------------------------------ |
| 模型    | 每个任务一个内存 Timeout + 一行 `delay_task`                                    | 少量 Job 定义 + Cron/固定频率，执行器跑一段代码 |
| 强项    | 单机、到期精度到 tick、插入/取消快                                                  | 多实例、失败重试、路由、管理台、分片             |
| 弱项    | 进程内调度；重启要整表灌轮；多实例要自己 CAS                                              | 不适合「一百万个一次性 Job」               |
| 和你们现状 | `execute_at = created_at + delay_ms`，启动 `max(0, execute_at - now)` 灌轮 | 业界标准是扫 `activate_at <= now`    |


```mermaid
flowchart LR
  buy[用户购买] --> row["权益表 PENDING + activate_at"]
  row --> xxl["XXL-JOB 每分钟扫到期行"]
  xxl --> grant["CAS 抢占后开通权限"]
  grant --> done[DONE 幂等]
```



时间轮路径是：购买时 `schedule` 入轮，到期回调开通。用户量一大，内存任务数、重启灌轮、滚动发布都会变成瓶颈。

## 为什么不要「一人一条 XXL-JOB」

XXL-JOB 的 Job 是**调度定义**（几点跑、跑哪个 Handler），不是「每个用户一个闹钟」。给每次购买动态 `add job` 会把调度中心打满，取消、改期、查询都别扭。正确用法只有一种：

```text
Job: grantDueEntitlements   cron: 0 * * * * ?   （或每 10 秒）
Handler:
  SELECT ... WHERE status='PENDING' AND activate_at <= now() LIMIT 500
  UPDATE ... SET status='RUNNING' WHERE id=? AND status='PENDING'
  开通权限（按订单号幂等）
  UPDATE ... SET status='DONE'
```

精度是「扫表间隔」（例如最多晚 1 分钟），权限开通通常可以接受。要对准到秒，再把间隔调短，或只对「未来 N 分钟内」的热数据用时间轮加速。

## 什么时候才用你们的时间轮

同时满足这些才优先 `lind-delay-task-web`：

- 单实例（或能接受自己做 claim，且重启灌轮量可控）
- 延时较短（分钟～小时），而不是「买了 30 天后开通」这种长尾全堆在内存
- 到期要尽快（秒级），扫表间隔不够用
- 开通逻辑已经幂等

即便如此，库仍是真相：`activate_at` 绝对时间；时间轮只负责「到点叫醒」。这和 [wheel/readme.md](lind-algorithm-framework/src/main/java/com/lind/algorithm/wheel/readme.md) 里的结论一致。

## 建议落地方式

1. 权益/订单表存 `user_id`、`sku`、`created_at`、`activate_at`（绝对时间）、`status`。
2. XXL-JOB 只注册一个 `grantDueEntitlements`，按上面的 SQL + CAS + 幂等开通。
3. 不要用时间轮给每个用户 `newTimeout`。
4. 若以后有「支付后 30 秒内必须开通」这类短延时高峰，再把「未来 5 分钟内」的行灌进时间轮做加速，XXL-JOB 扫表做兜底（漏网、重启、实例挂了）。



## 时间轮优先于任务调度的场景

可持久化时间轮（`lind-delay-task-web`：`execute_at = created_at + delay_ms`，重启按绝对时间灌轮）解决的是：**每个业务事件一个一次性闹钟，数量大、要准时、还要能取消**。任务调度解决的是：**少数固定节奏的批处理**。

优先用时间轮，当下面几条同时成立：

- 任务是**一次性、相对创建时刻的短延时**（秒～几小时），不是「每天 2 点」「每月结算」这种日历任务
- **并发创建/取消很高**（每秒大量 `schedule` / `cancel`），扫表的间隔和索引压力吃不消
- **到期精度要到秒级**，晚一分钟业务不能接受
- 单机或少量实例能扛住「未到期任务常驻内存 + 重启灌轮」；多实例必须靠库 CAS，不能各跑各的轮
- 失败可以重试，但主路径是「到点叫醒一次」，不是分片跑批


| 更适合时间轮                             | 更适合 XXL-JOB 扫表 / Cron            |
| ---------------------------------- | -------------------------------- |
| 未支付订单 15 分钟关单（下单即注册，支付成功立刻 cancel） | 每天凌晨对账、发月报、清理日志                  |
| 验证码 / 登录态 / 缓存键 5 分钟失效后的补偿动作       | 每小时汇总一次统计                        |
| 接口限流窗口、本地延迟重试（几十毫秒～数秒）             | 权限/会员「T+1 或 N 天后开通」这种可接受分钟级延迟的履约 |
| 延迟消息在单机内的近端触发（未来几分钟的热数据）           | 全量扫「已到期但还没处理」的兜底                 |
| 秒杀资格锁定 30 秒，超时释放库存                 | 跨机房、要控制台手动触发/分片的批任务              |


一句话：**闹钟很多、每个都不一样、还要秒级取消 → 时间轮；钟点固定、一次处理一批行 → 任务调度。** 两者可以叠用：时间轮管热路径，XXL-JOB 用一条 Cron 扫漏网的 `PENDING AND execute_at <= now()`。
