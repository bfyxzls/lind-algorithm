Bloom Filter 的核心特性是：**查“不存在”一定不存在，查“存在”只是可能存在**，会有假阳性，但不会有假阴性；标准 Bloom Filter 不支持删除，通常要配合分片、计数 Bloom、定期重建或精确存储。

## 1. 短链爬虫的 URL 重复判断

**目标**：避免爬虫重复抓取同一个 URL，尤其是多个短链可能跳转到同一个长链。

**Key 设计**：
- 规范化后的 URL，例如去掉 fragment、统一域名大小写、处理默认端口、query 排序等。
- 也可以同时存：
    - 原始短链 URL
    - 重定向后的最终长链 URL
    - 内容指纹，用于判断页面内容是否重复

**典型流程**：
1. 爬虫拿到一个 URL。
2. 先做 URL 规范化。
3. 查询 Bloom Filter：
    - 如果返回“不存在”：说明一定没抓过，加入待抓队列，并写入 Bloom Filter。
    - 如果返回“存在”：说明可能抓过，先跳过，或者去 Redis/DB 精确确认。
4. 抓取后，把最终 URL、内容指纹等也写入 Bloom Filter。

**为什么适合**：
- URL 量极大，用精确 Set 存所有 URL 内存成本高。
- Bloom Filter 可以用较小内存挡住绝大多数重复 URL。
- 假阳性只会导致少量新 URL 被误判为已抓，造成漏抓，所以通常会接一层精确存储做兜底。

**工程实践**：
- 常用 RedisBloom、分布式分片 Bloom。
- 按天/周分片，过期后删除整个分片，避免无法删除的问题。
- 对短链爬虫，最好先展开短链，再按最终 URL 去重。

## 2. 推荐系统的重复内容推荐判断

**目标**：避免给用户重复推荐同一内容，或避免重复内容进入推荐池。

这里通常有两类去重：

### A. 用户维度去重
避免同一个用户反复看到同一内容。

**Key 设计**：
- `userId + contentId`
- 或 `userId + itemId + 时间窗口`

**流程**：
1. 推荐系统召回一批候选内容。
2. 对每个候选内容，查询该用户的 Bloom Filter：
    - 不存在：可能没推荐过，可以进入排序/展示。
    - 存在：可能推荐过，过滤掉、降权，或去精确日志确认。
3. 推荐展示后，把 `userId + contentId` 写入 Bloom Filter。

**特点**：
- 每个用户一个 Bloom，或按用户分片。
- 可放在本地缓存、Redis、推荐服务内存中。
- 假阳性会导致少量未推荐内容被误过滤，影响召回多样性。
- 假阴性不会出现，所以已插入的内容不会被漏判为“没推荐过”。

### B. 内容库维度去重
避免相同文章、视频、商品重复进入推荐池。

**Key 设计**：
- 内容指纹，例如标题 SimHash、正文 SimHash、视频指纹、图片 pHash。
- 也可以用 `contentId` 或归一化后的内容 ID。

**流程**：
1. 新内容入库或进入候选池前，计算内容指纹。
2. 查询 Bloom Filter：
    - 不存在：认为是新内容，允许进入推荐池，并写入。
    - 存在：可能重复，进入精确相似度判断或人工/规则审核。

**工程实践**：
- 用户级去重通常需要时间窗口，可用按天/小时分片的 Bloom。
- 如果要删除或过期，使用 Counting Bloom Filter 或分片重建。
- 推荐系统通常不会只靠 Bloom 做最终判重，而是 Bloom 粗筛 + 精确日志/特征库确认。

## 3. 广告系统的内容曝光判断

**目标**：广告频控和曝光去重，避免同一用户短时间内反复看到同一广告、同一创意或同一活动。

**Key 设计**：
- `userId + adId`
- `userId + campaignId`
- `userId + creativeId`
- 通常还要加时间窗口，例如 `userId + adId + 1h`、`userId + adId + 1d`

**典型流程**：
1. 广告请求到来，系统召回一批候选广告。
2. 对每个候选广告，查询该用户对应的曝光 Bloom Filter：
    - 不存在：可能没曝光过，可以参与竞价或展示。
    - 存在：可能已经曝光过，按频控策略过滤、降权或不再展示。
3. 广告成功曝光后，把 `userId + adId + 时间窗口` 写入 Bloom Filter。

**为什么适合**：
- 广告请求量极大，要求低延迟。
- Bloom Filter 查询是 O(k)，内存占用小，适合做前置频控过滤。
- 可以在本地内存或 Redis 中按用户分片，减少网络和存储压力。

**误判影响**：
- 假阳性：用户可能没看过某广告，但被误判为看过，导致广告少曝光，影响广告收入。
- 假阴性：不会出现，否则会导致超频。
- 所以广告系统通常会把 Bloom 作为第一层过滤，后面接 Redis 计数器、实时数仓或精确频控服务做兜底。

**工程实践**：
- 按小时/天分片，过期删除整个分片，实现时间窗口频控。
- 高并发下常用本地 Bloom + Redis Bloom 两级。
- 需要精确频控时，Bloom 只负责挡掉大部分重复请求，最终以精确计数为准。

## 三个场景对比

| 场景 | Key 设计 | Bloom 作用 | 命中“存在”后处理 | 假阳性代价 |
|---|---|---|---|---|
| 短链爬虫 URL 去重 | 规范化 URL、最终 URL、内容指纹 | 判断 URL 是否已抓取 | 跳过或精确确认 | 漏抓少量新 URL |
| 推荐系统重复推荐 | userId+contentId、内容指纹 | 判断用户是否看过、内容是否重复 | 过滤、降权、精确确认 | 少推内容，影响多样性 |
| 广告曝光判断 | userId+adId+时间窗口 | 判断用户是否已曝光 | 频控过滤、降权 | 少曝光广告，损失收入 |

---

## 总结

Bloom Filter 在这三个场景中的共同模式是：

1. **写入**：处理过的 URL、推荐过的内容、曝光过的广告，写入 Bloom Filter。
2. **查询**：新 URL、推荐候选、广告候选先查 Bloom。
3. **判断**：
    - 不存在 → 一定没处理过，可以继续。
    - 存在 → 可能处理过，过滤、跳过、降权或精确确认。
4. **定位**：Bloom Filter 通常作为**前置去重/频控层**，用少量内存挡住大量重复请求。
5. **兜底**：对准确性要求高时，配合 Redis Set、数据库、实时计数、Counting Bloom 或时间分片重建。

一句话：**Bloom Filter 适合“海量集合存在性判断 + 允许少量假阳性 + 不能有假阴性”的去重场景，在短链爬虫、推荐去重、广告频控中都是低成本前置过滤器。**
